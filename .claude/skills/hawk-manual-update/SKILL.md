# hawk-manual-update: HAWK 機能取扱説明書の巡回更新

## 全体像

- **正はマスターシート**（`hawk_manual/config.json` の `master_sheet_id`）。スライドは生成物なので直接直さない。
- スライドは3種類。
  - 下書き版 … 全行。片山の見え方確認用。お客様には出さない。
    **版ごとに別ファイル**（下書きv1, v2, …）で残し、マスターの「版管理」タブに URL・ページ数・変更内容を記録する。
    `python3 build_slides.py draft --note "変更内容"` で次の版を作る。同じ修正回の中で作り直すときは
    `--same-version`（版番号を上げず最新版を上書き）。`draft_presentation_id` は常に最新版を指す
  - 本番版（`prod_presentation_id`）… 承認済 × 提供中 の行だけ。URL 固定で中身だけ差し替わる。お客様にはこの閲覧リンクを渡す
  - 本番・簡易版（`prod_lite_presentation_id`）… 本番のうち「簡易版」チェックの行だけ
- 列定義は `hawk_manual/schema.py`。運用ルールはシートの README タブ。

## 巡回の手順（3日おき）

作業ディレクトリは `hawk_manual/`。

1. **後始末**: `python3 housekeep.py`（承認日の記入、同IDの古い承認済行を置換済に）
2. **前回の巡回日時を調べる**: 版管理タブで 種類=`巡回` の最終行の 生成日時。無ければ 7日前。
3. **新着を読む**（読み取り専用。Slack には一切書き込まない）:
   - `#hawk-社内利用`（C0A276ZULRZ）と `#hawk-product`（C081CRUG68L）の、前回巡回以降のメッセージとスレッド返信。
   - 対象: リリース告知、仕様の「できる/できない」回答、不具合と回避策、提供終了。
   - 対象外: 日程調整、会食、営業パイプライン、競合の話（HAWK 自身の可否を述べている部分は対象）。
   - リンクされた Docs/Slides に仕様が書かれていれば `gog docs cat` / `gog slides raw` で読む。
4. **シートに下書きで書く**: 追加分をタブごとに TSV（1行目=列名）にして `python3 load_tsv.py <タブ名> <file.tsv>` で追記する。
   （values.append は使わない。チェックボックス列のせいで1000行目付近に書かれてしまう）
   - 新機能 → 機能一覧に新しい機能IDで行を追加。承認=`下書き`。提供状態は告知の文言どおり（リリース済=提供中、開発中/予定はそのまま）。
   - 既存機能の仕様変更 → **承認済の行は書き換えない**。同じ機能IDで新しい行を末尾に追加（承認=下書き）。メモに「旧: …」と差分を書く。
   - 画面が増えた/変わった → サイトマップに同じ要領で追加。
   - 「こうしたい→この機能」が読み取れたら逆引きにも下書きで追加。
   - すべての変更を **更新履歴** に1行（検知日=今日、リリース日=告知日、ソース=Slack permalink、反映状況=下書き）。
   - 判断がつかないものは **要確認** タブに起票（誰に聞くか: 開発=藤川さん/Ayayaさん、仕様=Yugoさん）。推測で機能一覧に書かない。
   - 書く前に既存行を読み、同じ内容が既にあれば足さない（冪等にする）。
5. **スライドを作り直す**:
   - `python3 build_slides.py draft`
   - `python3 build_slides.py prod --archive` と `python3 build_slides.py prod --lite --archive`
     （本番は承認済の行しか載らないので自動で回してよい。内容が前回と同じなら PDF 保存はスキップされる）
6. **巡回記録**: 版管理タブに `[今日, 今の日時, "巡回", "", "", 追加した行数, "新着N件 / 要確認M件"]` を append。
7. **報告**（セッションの最終メッセージ）: 追加した下書き行（ID・機能名・ソース）、要確認の件数、
   承認待ちの総数、下書き版と本番版の URL。新着ゼロなら「新着なし」の1行だけ。

## 片山がやること

- マスターシートで下書き行を見て、承認列を `承認済` / `差戻し` にするだけ。次の巡回で本番に反映される。
- すぐ本番に出したいときは「マニュアル本番反映して」と依頼 → 手順1と5だけ実行。
- 見せ方（デザイン・文言の型）を変えたいときは `build_slides.py` の `build()` を直す（テンプレートは1箇所）。

## スクショ

- 片山がスクショ用フォルダ（`screenshot_folder_id`）に「S-xx_名前.png」で置く → 生成時に自動で
  伏せ字加工（`sanitize.py`: OCR でメール・アカウント名・ワークスペース名・人名・広告アカウントID 等を
  hoge 表記に置換）し、「加工済み（自動）」フォルダに保存、サイトマップの「スクショ」列に紐づく。
- 非公開の Drive 画像は Slides API が直接読めないため、pptx 経由で取り込む（`assets.resolve_drive_images`）。
  画像を一般公開にはしない。
- 伏せ字ルールを足すときは `sanitize.py` の REPLACE に追記する。加工後は必ず目視確認する。

## 注意

- お客様向けの本番版に **開発中・予定の機能は載せない**（提供状態=提供中だけ）。下書き版には載る。
- これは導入・オンボーディング後のお客様向けの **操作ガイド**。サービス概要・導入メリット・工数削減・
  他社比較・料金/契約・セキュリティ等の FAQ は載せない（承認=差戻し、メモ「操作ガイド対象外」）。
- Slack への投稿・リアクション、マスター以外の Drive ファイルの編集はしない。
- 承認列を自分で `承認済` にしない（承認は片山だけが行う）。
