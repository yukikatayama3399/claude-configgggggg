# hawk-gijiroku: Gemini 文字起こしからの「厚め議事録」作成

社内の意思決定系ミーティング（料金・契約条件・プラン設計など、細かい論点が多い会）の
議事録を作る。**Gemini の「メモ」タブの要約だけで済ませず、文字起こし全文を読んで**
決定・未決・宿題・数字を漏れなく拾うのがこのスキルの存在理由。

## 入力（依頼文から特定する）

| 入力 | 例 | 無い場合 |
|---|---|---|
| Gemini 自動メモの Doc URL（`?tab=` 付きなら文字起こしタブ） | `docs.google.com/document/d/<id>/edit?tab=t.xxxx` | 依頼者のカレンダー当日イベント名で Drive 検索（`〇〇 - Gemini によるメモ`） |
| 手元メモ（Slack に貼った箇条書き等） | 「▼ツナグ＆アクセス …」 | 文字起こしのみで作る |
| アジェンダ（目的・決定済み前提・議題） | 「■ 目的 ■ 決定済みの前提 ■ アジェンダ」 | 文字起こし冒頭から推定し「（推定）」と明記 |
| 参考資料 URL（Slides / Docs / Sheets） | 顧客の声マップ・料金提案スライド | 参考資料セクションは元データのみ |
| 出力先 | 「中西宛ての Slack DM に下書きで」 | **既定: 依頼者本人への Slack DM 下書き**（勝手に送信しない） |

## Step 1: 元データを全部取る（読み取り専用）

Gemini メモ Doc は **複数タブ構成**（`メモ` / `文字起こし`）。
`gog docs cat` は先頭タブしか返さないので、必ず gws で全タブを落とす。

```bash
S=.claude/skills/hawk-gijiroku/scripts
OUT=<scratchpad>/gijiroku
python3 $S/dump_gdoc_tabs.py "<Doc URL or ID>" "$OUT"        # tab_<tabId>.txt が出る
python3 $S/dump_slides_text.py "<Slides URL or ID>" ...      # 参考スライドの全文字（表・グループ含む）
```

- 文字起こしは 1 時間で 2〜3 万字。**全文を読む**（sed -n で 150 行ずつ程度に分けて）。
  Gemini の「概要」「次のステップ」「詳細」は下書きの骨にはなるが、
  数字・条件・言い回し（誰が何を懸念したか）は文字起こしにしか無い。
- 参考資料は「読み込むだけ」でなく、要点 1〜3 行と URL を議事録の参考資料欄に添付する。
- 資料の作成者を特定したいときは `gws drive files get --params '{"fileId":"...","fields":"owners(displayName,emailAddress)"}'`。

## Step 2: 読み解きのルール

- **誤変換を前提に読む**。よくあるゆれ（HAWK 文脈）:
  繋ぐ／つさん＝ツナグ、アクセスプロレス＝アクセスプログレス、アドン＝アドオン、
  重量課金＝従量課金、ロンズ＝Bronze、大体／売＝媒体、キャンペ／CP＝キャンペーン、
  とさん／ともさん／トンさん＝tomo さん、ヒデさん＝中西、ゆ君＝片山、
  リールデスク／ディールディスク＝DealDesk、コパイロット＝Copilot、エース／レッド＝Red（OEM 契約）。
  新しいゆれを見つけたら議事録末尾の補足に「対応表」として残す。
- **数字は文字起こしと手元メモを突合**する。会議中に届いた先方回答（例: 8月実績 224・希望 400）は
  文字起こし内の「返信来た」直後に出るので拾う。
- **発言者の帰属は確信がある時だけ**書く（資料作成者・一人称・役割から判断）。
  迷う時は「（片山）」等を付けず事実だけ書く。推測を事実のように書かない。
- **決定／未決／宿題を分ける**。「〜がいい気がする」「〜で良さそう」は合意扱いにしてよいが、
  「要確認」「決めの問題」「別途整理」と言われたものは未決に落とす。
- 「なぜそう決めたか」（理由・懸念・却下した代替案）を 1 行添える。後日 tomo さん等に
  展開する時に理由が無いと通らない。
- 雑談・移動・イベント予定は末尾の「日程・イベント」「補足」に 1〜2 行で残す（消さない）。

## Step 3: 構成テンプレート（厚め版）

```
【議事録】<テーマ>（<日付> <開始〜終了> 約Nh）
日時｜参加｜形式｜元データ URL（文字起こしタブ）

■ 目的（アジェンダ）          ← 依頼者のアジェンダをそのまま。決定済み前提も 1 行で
■ 結論サマリ（決定・合意事項）  ← 論点ごとに A/B/C…。太字で結論、直下に条件・理由・代替案
■ 議論の詳細                  ← 時系列。見出しに文字起こしのタイムスタンプ範囲（00:10〜00:17）
■ 未決事項・今後の論点
■ Next Action                 ← 番号＋【担当】＋内容＋期限。Slack では表を使わず番号リスト
■ 参考資料                    ← URL ＋ 要点（何枚目に何があるか）。元データ Doc も載せる
■ 補足メモ                    ← 運用メモ・誤変換対応表・検証中ツールの所感
```

分量の目安: 1 時間の会議で 1.5〜2 万字（Slack 1 メッセージ上限 4 万字以内）。
「通常の議事録より厚く、要点は全部」が発注の趣旨。短くまとめ直さない。

## Step 4: 出力先

既定は **Slack の DM 下書き**（`mcp__Slack__slack_send_message_draft`、`channel_id` に相手の
user ID）。**送信はしない**。Drive / Docs には残さない（明示依頼があれば下記の Doc 版を作る）。

原稿は必ず Markdown ファイル（`<scratchpad>/minutes.md`）に一度書き、Slack にも Doc にも
**同じ原稿から**出す（二重メンテしない）。

### Doc 版（「docs にもして」「文字詰めて」と言われたら）

```bash
gog --account yuki.katayama@fout.jp docs create "議事録_MMDD_<テーマ>（<参加者>）"   # → id
python3 .claude/skills/hawk-gijiroku/scripts/minutes_to_gdoc.py <scratchpad>/minutes.md <docId>
```

- 「文字詰め」体裁: 本文 9pt・段落間隔 0・行間 100%・余白 36/40pt、■ 見出しだけ 10.5pt＋上余白 7pt、
  空行と `---` は捨てる、Next Action の表は番号リストに変換。
- URL は gdocs-hyperlink スキルの流儀で本物のリンクにする（UTF-16 単位で範囲計算。スクリプトが担当）。
- Doc は My Drive 直下に作られる。顧客フォルダ等へ入れる指示があれば `gog drive move` で移す。
- 作成後は `gog docs cat` で読み返し、`gws docs documents get` で link 付き textRun が期待数あるか確認する。

- 中西（Hideyuki Nakanishi, hide@fout.jp）: `U1FCLBC31`
  ※ Slack の表示名は `hide`。`中西` で検索しても出ないので `hideyuki` / `nakanishi` で探す
- 自分（片山）: `U0B7FMCR8JU`
- 相手が不明なら `slack_search_users` → 資料オーナー（`gws drive files get` の owners）で裏取り
- Slack 向け整形: 表は番号リストに変換、`---` は使わない、太字は `**〜**`、
  インデントは全角スペース。URL は素のまま（自動リンク）
- `draft_already_exists` が返ったら: その相手との DM に既存下書きがある。依頼者に
  「既存下書きを消すか、本文をチャットに出すか」を聞く（勝手に上書きしない）

## Step 5: 完了報告

チャットには「下書き先／文字数／拾った決定事項の件数／未確認として残した点（固有名詞の表記など）」
を短く報告する。議事録本文はチャットに再掲しない（Slack 下書きが正）。
