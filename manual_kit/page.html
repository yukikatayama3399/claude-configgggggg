HAWK 方式・ほかのプロダクトに展開するためのプロンプト集

機能取扱説明書 横展開キット

HAWK で作った「機能取扱説明書」と同じものを、自分のプロダクトでも作るためのプロンプト集です。資料をフォルダに置いて、プロンプトを Claude Code に貼れば、管理シートと取説スライドができます。そのあとは定期巡回で新機能や FAQ の候補が Slack に届き、承認した分だけ取説に入ります。

元になった仕組み HAWK 機能取扱説明書作成 片山更新 2026-10-16

01やりたいこと

作る

資料を全部読ませて、取説を一発で作る

スクショ・操作動画・サンプルレポート・既存資料と、Slack・メール・会議メモをまとめて読み、管理シートと取説スライドを作ります。

回す

管理シートを常に最新に保つ

毎日または毎週、Slack・メール・会議メモ・Drive を巡回し、新機能・仕様変更・新しい質問を拾ってシートに候補として足します。

承認する

入れるかどうかは Slack で決める

候補ごとに Slack に通知が来ます。✅ 入れる／❌ 入れない／✏️ 直して入れる、を押すだけ。承認した分だけ取説が更新されます。

HAWK の実績：2026-10-09 に初版を作り、同じ日に確定版をお客様向けの固定 URL で公開。2026-10-16 時点で機能113行・画面のスクショ付き 81 ページ。月・木の巡回で承認依頼が届き、承認分は自動で下書きに入っています。

02進め方

  1. 人・1〜2時間（大半はスクショ撮影）資料を集めて Drive のフォルダに置き、下の「設定」の空欄を埋める
  2. Claude・1セッション（放置で OK）プロンプト①「初回構築」を貼る → 管理シートと下書き v1 ができる
  3. 人・30分〜シートを見て直し、全件承認して、下書きを作り直して と頼む。「要確認」の質問は開発に聞いて回答を返す
  4. 人の一言マニュアル本番に反映して → お客様用の固定 URL ができる。以後 URL は変わらず中身だけ更新される
  5. Claude・15分プロンプト②「巡回と承認フロー」を貼る → 定期巡回が登録され、1回目が動く
  6. 人・普段Slack の承認依頼に ✅ ❌ ✏️ を押すだけ。急ぐときやスクショ追加は ③ の一言で頼む

# 読む資料

## A. 渡す資料（全部読む。読んだものはすべて「ソース一覧」タブに登録する）
- 画面キャプチャ（{{SCREENSHOT_FOLDER}}）
  - 1枚ずつ中身を見て、どのメニューのどの画面かを判定し、画面ID を振る。作業フォルダ内に「スクショ_加工済み」フォルダを作り、「S-01_ログイン.png」のような名前でコピーを置く（元ファイルは触らない）。
  - メールアドレス・人名・アカウント名・ワークスペース名・広告アカウントID・クライアント名やブランド名を OCR で見つけ、サンプル表記（sample@example.com、サンプル広告株式会社 など）に置き換えた加工版を作る。画面ごとに追加ルールを足せるよう、ルールは JSON にしてリポジトリに置く。
  - 加工後は必ず1枚ずつ自分の目で見直す。残っていたらルールを足して作り直す。
  - 暗い余白・モーダルの背景・ブラウザ枠は切り落とす。
- 操作デモ動画（{{VIDEO_FOLDER}}）
  - ダウンロードし、ffmpeg で画面が切り替わったところのコマを切り出して読む。操作の順番・画面遷移・ボタン名・入力例を拾う。
  - 同じフォルダに文字起こしや台本があれば一緒に読む。Meet の録画なら同名の文字起こし Doc を探す。
  - 動画のコマはスクショの代わりに使わない（画質が粗く、実データが映る）。スクショが無い画面は「要確認」に「この画面のスクショが欲しい」と起票する。
- サンプルレポート（{{SAMPLE_REPORTS}}）
  - 全部読み、レポートの種類・ページ構成・各指標の意味・出力条件を、機能一覧のレポート章と FAQ に落とす。
  - お客様に見せてよい見本は {{SAMPLE_REPORT_PUBLIC}}。取説のレポート画面のページからリンクする。
- 既存資料（{{EXISTING_DOCS}}）
  - {{CANONICAL_DOCS}} は正本として他より優先する。古い記述（後のリリースで変わったもの）は新しい出典で上書きし、メモに「旧: …」と残す。

## B. 自分で探しに行く資料（読み取りだけ。投稿・送信・編集はしない）
- Slack: {{WATCH_CHANNELS}} の過去 {{LOOKBACK}} 分を、スレッド返信まで全部読む。さらにワークスペース全体を {{KEYWORDS}} で検索し、他のチャンネルで出た仕様の回答・リリース告知・お客様からの質問も拾う。DM は読まない。
- Gmail: {{KEYWORDS}} で検索。リリースノート、仕様の回答、お客様からの操作の質問を拾う。
- 会議メモ: Drive の自動議事録（「Gemini によるメモ」など）と議事録 Doc を、本文の全文検索（fullText contains）で {{KEYWORDS}} を含むものから集める（日本語は title contains が効かないので fullText を使う）。オンボーディング・商談・社内の仕様会議の Q&A は FAQ の材料になる。文字起こしの誤変換は {{NAME_VARIANTS}} を手がかりに補って読む。
- Drive: 名前に {{PRODUCT}} を含む仕様書・リリースノート・スライド。
- 公開ページ: {{PUBLIC_PAGES}}
- リンク先の Docs / Slides / Sheets に仕様が書かれていれば、それも開いて読む。

# マスターシートの構成（このとおりに作る）

タブと列:
- README … 運用ルール（自由記述）。冒頭に「最新の下書きURL」と「本番の固定URL」を置き、スライドを作るたびに自動で書き換える。
- 機能一覧 … 機能ID / カテゴリ / 画面ID / 機能名 / できること / 設定項目・選択肢 / 何のため（目的） / 対応範囲 / 制約・注意 / 提供状態 / 承認 / 簡易版 / ソース / 初出日 / 最終更新日 / 承認日 / メモ
- サイトマップ … 画面ID / 階層1 / 階層2 / 階層3 / 画面名 / URLパス / 遷移元 / 遷移先 / この画面でやること / 関連機能ID / スクショ / 承認 / ソース
- 逆引き … UCID / カテゴリ / やりたいこと / 手順（概要） / 使う機能ID / 承認 / 簡易版 / ソース / メモ
- FAQ … FAQID / カテゴリ / 質問 / 回答 / 提供状態 / 関連機能ID / 承認 / 簡易版 / 出典 / 最終確認日 / 要確認 / メモ
- 更新履歴 … 検知日 / リリース日 / 種別（追加・変更・提供終了・不具合） / 対象ID / 内容 / 提供状態 / ソース / 反映状況 / 承認日
- 要確認 … QID / 対象ID / 確認したいこと / 誰に聞くか / 回答 / ステータス / 起票日
- ソース一覧 … SID / 種別 / タイトル / URL / 日付 / 重要度 / メモ
- 版管理 … 版 / 生成日時 / 種類（draft・prod・巡回・承認依頼） / スライドURL / PDF / 承認済行数 / メモ

値の決まり:
- 承認: 下書き（＝候補）/ 承認済 / 差戻し / 置換済 のプルダウン。
- 提供状態: 提供中 / 開発中 / 予定 / 未対応 / 提供終了 / 不明 のプルダウン。
- 簡易版: チェックボックス（よく使う基本機能だけ TRUE）。
- ID: 機能ID は F-カテゴリ略号-連番（例 F-RPT-003）、画面ID は S-連番、逆引きは UC-連番、FAQ は Q-連番。一度振った ID は変えない・使い回さない（やめた機能は提供状態を「提供終了」にする）。
- カテゴリと略号は、使う頻度の高い順に 8〜10 個決めて固定する。スライドの章もこの順に並ぶ。
- 1行目は固定表示、列幅・折り返しを整えて人が読める見た目にする。
- 初回に作った行は全部「承認=下書き」。{{OWNER}} がシートを見て直したあと「全件承認して」と言ったときだけ承認済にする。

# 書き方のルール
- 1行に1機能。「できること」は {{READERS}} が読んで分かる、です・ます調の1〜2文。社内用語・開発用語は使わない。
- 「ソース」列には必ず出典を書く（Slack の permalink、Doc の URL、資料名とページ）。出典が無いことは書かない。
- 資料同士で食い違ったら（例: 商談では「できない」、後の社内会議では「できる」）、新しい方を仮に書き、要確認タブに両方の出典つきで起票する。誰に聞くか（{{ASK_WHO}}）も書く。
- お客様の社名・個人名・メールアドレスはシートに書かない。機能の可否だけを書く。
- {{OUT_OF_SCOPE}} は取説に入れない。拾った場合は 承認=差戻し、メモ「取説対象外」。
- シートへの追記に values.append は使わない（チェックボックス列があると 1000 行目付近に書かれてしまう）。最終行を調べて行番号を指定して書く。TSV（1行目=列名）を読んで指定タブに追記するスクリプトを作って使う。
- 書く前に既存の行を読み、同じ内容があれば足さない（何度流しても重複しないようにする）。

# スライドの作り方
- Google Slides API（gws の presentations batchUpdate）を叩く Python スクリプトで、マスターから毎回まるごと作り直す。スライドを手で直さない（直したい点はマスターかスクリプトを直す）。
- 構成: 表紙（機能数・画面数・逆引き数・FAQ数）→ 目次と読み方 → 全体像（工程の流れと各工程の機能） → サイトマップ（画面構成と掲載ページ） → 最近の更新 → カテゴリごとの章（1画面1ページ: 左にスクショ、右にその画面の機能の表。【設定】【目的】【注意】） → 逆引き → FAQ。
- 載せるのは 承認=承認済 の行だけ。下書き版は 開発中・予定 も載せてよい。本番版は 提供状態=提供中 だけ。
- 下書きは版ごとに別ファイル（v1, v2, …）。作るたびに版管理タブに1行足し、README の最新 URL を書き換える。
- 本番版は {{READERS}} に渡す固定 URL。URL を変えず中身だけ上書きし、作り直すたびに PDF を日付つきで保存して版管理に残す。今回は本番版を作らない（{{OWNER}} の指示があったときだけ作る）。
- 非公開の Drive 画像は Slides API から直接読めないので、pptx を経由して取り込むなどの回避を入れる。
- デザインは {{BRAND}}。文字が枠からあふれるときは自動で文字を小さくする。「…」で切らない。

# やりたいこと
{{SCHEDULE}} に自動で巡回し、毎回次の3つをやる。
1. 前回の承認依頼への回答（✅ / ❌ / ✏️）を読んでマスターに反映する。1件でも承認済にしたら、下書きスライドを新しい版で作り直す。
2. 前回の巡回以降の新着（Slack・メール・会議メモ・Drive）から、新機能・仕様変更・FAQ候補・逆引き候補・提供終了・不具合と回避策を拾い、マスターに「承認=下書き」（候補）で追記する。
3. 候補が1件以上あれば、Slack {{APPROVAL_CHANNEL}} に {{OWNER}} 宛ての承認依頼を投稿する。候補ゼロなら何も投稿しない。

# 拾う範囲（読み取りだけ）
- 「前回」= 版管理タブの 種類=巡回 の最後の行の日時。無ければ7日前。
- Slack: {{WATCH_CHANNELS}} の前回以降の全投稿とスレッド返信。加えてワークスペース全体を {{KEYWORDS}} で検索（DM は除く）。
- Gmail: 「{{KEYWORDS}} after:<前回の日付>」で検索。リリースノート、仕様の回答、お客様からの操作の質問。
- 会議メモ: 前回以降に更新された自動議事録（Gemini によるメモ）と議事録 Doc のうち、本文に {{PRODUCT}} が出るもの。
  特に、行頭が「【取説】」の行は必ず候補にする。会議に出た人が議事録に「【取説】〇〇はできる」と1行書いておけば、次の巡回で確実に拾われる。
  （全文検索の索引は追記直後に遅れることがあるので、直近に更新された議事録は本文を直接読んで確かめる）
- Drive: 名前に {{PRODUCT}} を含む仕様書・リリースノートで、前回以降に更新されたもの。
- 拾わないもの: 日程調整、会食、営業案件の進捗、{{OUT_OF_SCOPE}}。
- 判断がつかないものは推測で書かず要確認タブへ（誰に聞くか: {{ASK_WHO}}）。
- シートに既にある内容は足さない（毎回同じ候補を出さない）。
- お客様の社名・個人名・メールアドレスはシートにも Slack にも書かない。

# シートへの書き方
- 新機能 → 機能一覧に新しい機能ID で行を追加。提供状態は告知の文言どおり（リリース済=提供中、開発中・予定はそのまま）。
- 既存機能の仕様変更 → 承認済の行は書き換えない。同じ機能ID で新しい行を末尾に足し、メモに「旧: …」と差分を書く。承認されたら古い行を「置換済」にする。
- 新しい質問と回答 → FAQ に追加。「こうしたい → この手順」が読み取れたら逆引きにも追加。画面が増えた・変わった → サイトマップに追加。
- どの変更も更新履歴に1行（検知日=今日、リリース日=告知日、ソース=permalink、反映状況=下書き）。

# 承認フロー（Slack）
親メッセージを1件:
「<@{{OWNER_SLACK_ID}}> 【{{PRODUCT}} 取説】取り込み候補が N 件あります。各候補に ✅（入れる）/ ❌（入れない）/ ✏️（直して入れる）を付けてください。次の巡回で ✅ の分だけ下書きに反映します。本番（お客様に渡しているURL）には反映しません。」

候補ごとにスレッド返信を1件ずつ（番号つき）:
「#2 【FAQ追加】Q. 〇〇はできますか？
A. （回答案を1〜2文）
入れ先: FAQ 新規 Q-071（関連 F-OPS-012）
出典: <permalink>
✅ 入れる ／ ❌ 入れない ／ ✏️ 直して入れる（このスレッドに直した文を書く）」

種別ラベルは【新機能】【仕様変更】【FAQ追加】【逆引き追加】【提供終了】【不具合・回避策】のどれか。
仕様変更は「旧: … → 新: …」を必ず並べて書く。

回答の読み方（次の巡回の最初にやる）:
- 候補ごとのスレッド返信に付いたリアクション（white_check_mark / x / pencil2）と、{{OWNER}} の返信を読む。「1,3 OK / 2 NG」のようなまとめ返信も受け付ける。
- ✅ → 承認=承認済、承認日=今日、更新履歴の反映状況=承認済。
- ❌ → 承認=差戻し、メモ「NG（日付）」。
- ✏️ と修正文 → 修正文で行を直して承認済にし、その候補のスレッドに「直して反映しました」と1行返す。
- 反応なし → 保留。次回もう一度見る。3回続けて反応が無ければ、親メッセージのスレッドに1回だけリマインドする。
- 投稿したら版管理タブに [今日, 今の日時, 承認依頼, "", "", 候補数, "未処理 / ts=<親のts> / #1=ID, #2=ID…"] を記録する。処理したらメモを「処理済 / 承認 n件・NG m件・保留 k件」に書き換える（保留が残れば「未処理」のまま）。
- 巡回のたびに版管理タブに [今日, 今の日時, 巡回, "", "", 候補数, "新着N件 / 承認反映M件 / 要確認K件"] を記録する。

06HAWK で実際につまずいたところ

プロンプトには対策を入れてあります。運用中に変だと思ったらここを見てください。

スライドを手で直すと消える

スライドは管理シートから毎回作り直すので、直接の修正は次の生成で消えます。直すのはシートかスクリプト。

承認済の行を上書きすると履歴が消える

仕様変更は同じ ID で新しい行を足し、承認されたら古い行を「置換済」にします。

追記が 1000 行目に飛ぶ

チェックボックス列があるとシートの追記 API が末尾を誤判定します。行番号を指定して書きます。

伏せ字の漏れ

メールアドレスの一部、薄く表示されたヘッダーの名前、URL の中の ID、ブランドのロゴ、画面下端で見切れた行で漏れました。自動加工のあとに必ず目で見ます。

非公開の画像がスライドに入らない

Slides API は共有されていない Drive 画像を読めません。pptx を経由して取り込みます。

文字起こしの誤変換

「フォーク／ホーク／航空」が HAWK、「予見」が与件、「マジ」がマージン。表記揺れは最初に教えておきます。

資料どうしで「できる／できない」が食い違う

HAWK では初回だけで5件以上。推測で書かずに「要確認」に起票し、開発に聞いて回答を返します。

下書きと本番を取り違える

お客様に渡すのは本番の固定 URL だけ。下書きは版ごとに URL が変わる社内用です。

毎日巡回だと版が増えすぎる

承認が1件以上あった日だけ新しい版を作り、候補がゼロの日は Slack に投稿しません。

Google への書き込みがコネクタでできない

Drive コネクタは読み取り中心で、シートのセルやスライドに書けません。gog / gws を使います。
