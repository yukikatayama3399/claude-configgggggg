# hawk-recruit-signal-sweep ランブック

## 目的
「SNS/Meta広告の運用者を募集中」の会社を求人サイトの本日新着から毎営業日拾い、
HAWKアタックリストに新規ぶんだけ自動追記し、採用逼迫シグナルの強い会社（S級）だけSlackに要約通知する。
求人＝①既にキャンペーンが回っている×②運用リソースが足りていない、の両シグナルが立った状態なので、
HAWKの「接触時のタイミング問題」を求人情報がそのまま解決してくれる。

## トリガー
- cron: `0 9 * * 1-5`（平日 09:00 JST / Asia/Tokyo）
- 他ルーティン（hawk-url-index-original-refresh も 9:00）と衝突するため、約10分ジッターを許容
- **Claude Code 起動中にのみ発火**。Macスリープ / Claude Code 停止中の回はスキップ（＝取りこぼした日があっても、翌営業日に「本日新着」で自然に回復する設計。過去日を遡らない）

## 実行内容

### ステップ1: 収集（媒体フォールバック方式）
取得元を以下の優先順で回り持ちし、**1媒体あたり最大5ページまで**に制限する（人が閲覧する範囲。機械的な大量クロールはしない）。

1. 求人ボックス（kyujinbox.com）
2. スタンバイ（stanby.com）
3. Googleしごと検索

- 検索条件（求人ボックスの実証済みURLパラメータ）:
  - キーワード「Meta広告 運用」（最もノイズが少なくHAWK適合度が高い。本日新着で約80件/日）
  - 正社員 / 24時間以内 / 社名非公開求人を除く（`?e=1&u=1&f=9`）
  - サブクエリとして「SNS広告運用」も回すが、重複率が高いので最大3ページで打ち切り
- **CAPTCHA / ログイン要求 / bot検知を検出したら、その媒体は当日スキップして次の媒体にフォールバック**する。突破は試みない（会社アカウントでの規約違反自動化はしない）。
- **全媒体がブロックされた日だけ**、Slackの自分宛DMに「本日スイープ全媒体ブロック、手動確認要」と通知して終了。

### ステップ2: 正規化とdedup
- 会社名を正規化（㈱⇔株式会社、全角半角、前後空白の除去）
- 既存の突合対象:
  - HAWKアタックリスト（ID: 1iyhwVNhN_HJNdIBL_pREhrhBdQu2it5ktFOYq-DDm_w、miwata所有）の全タブ
  - 本ルーティン専用の取得済み台帳（下記ledger）
- **新規会社のみ**を後続処理に渡す。dedupロジックは #competitor-watch のGoogle Sheets台帳方式を流用。
- 専用ledger（取得済み会社の記録用）: **発行済み（2026-08-17）**
  - ID: `1ezYY2PbszQaRcjWA85fMGbvJ4kmPGb6e2AAJwLlUGAo`
  - タブ名: `ledger`（13列。取得日／媒体／会社名(正規化)／会社名(原文)／求人タイトル／シグナル／S級判定／勤務地／検索クエリ／種別／サイトURL／電話／備考）
  - URL: https://docs.google.com/spreadsheets/d/1ezYY2PbszQaRcjWA85fMGbvJ4kmPGb6e2AAJwLlUGAo/edit

### ステップ3: エンリッチ（新規会社のみ）
- 各社について web_search で「会社名＋会社概要／電話」を1〜2回検索し、サイトURL・代表電話・所在地・種別（代理店/事業会社/媒体社）を補完
- 代表電話が非公開の場合は「非公開（フォーム/採用窓口）」と明記
- 競合大手（サイバーエージェント、電通G、博報堂G本体等）は種別「競合」フラグを立て、通知対象から除外（OEM文脈で別途判断）

### ステップ4: 出力
1. **アタックリスト追記**: HAWKアタックリストに新規タブ「採用シグナル」を用意し、以下の列で追記
   （取得日／媒体／会社名／求人タイトル／シグナル／勤務地／検索クエリ／種別／サイトURL／電話／備考）
   - Sheets書き込みツールが無い環境では、貼り付け用TSVをローカル出力し、パスをSlackに通知
2. **専用ledgerに全新規会社を追記**（次回dedup用）
3. **S級シグナル通知**: 下記の「S級判定」に該当する会社だけ、Slackの自分宛DMに要約通知（会社名・シグナル・サイトURL・電話・一言トーク）

### S級判定（Slack通知する条件。1つでも該当でS級）
- 同一社が同日に複数職種で募集（運用キャパが本気で不足）
- 「大量募集」「急募」タグ
- 求人文に「内製化」「一人目」「立ち上げメンバー」「増員」
- 予算規模が月数千万〜億の記載
- D2C×Meta/TikTokの少額多頻度（Cyberbuzz型の勝ちパターン）

## 安全設計（一方向・非破壊）
- **読み取りと追記のみ**。既存アタックリスト行の編集・削除は一切しない（追記onlyの一方向）
- 応募ボタン・送信系は一切触らない（閲覧のみ）
- CAPTCHA突破・プロキシ迂回・検知回避は行わない（会社アカウントのレピュテーションリスクを生む線は越えない）
- メール送信・カレンダー変更は本ルーティンでは行わない（収集と台帳化まで。架電・メールは人間が判断）

## チューニングのメモ
- **キーワード**: 「Meta広告 運用」が本命。取れ高が落ちたら「運用型広告」「Instagram広告 運用」を追加。「未経験」系はテンプレ量産ノイズが多く非推奨
- **除外フィルタ**: 「社名非公開求人を除く」はON推奨。「人材紹介の求人を除く」はONにすると件数が激減する（99→1件の実績）ので**使わない**
- **ページ上限**: 5ページ/媒体。CAPTCHA頻発なら3ページに下げる
- **通知頻度**: S級が多すぎる場合は判定を「複数求人 or 大量募集」のみに絞る
- **媒体順**: 求人ボックスが最も安定。ブロック頻発するようなら順序を入れ替え

## 実行環境の制約（2026-08-17 実測）

**本ルーティンは会社Mac上のローカル実行専用。クラウド Routine では動かない。**

他のルーティン（hawk-url-index-original-refresh 等）はクラウド Routine
（`create_trigger`）で動いているが、本ルーティンだけは同じ方式に乗らない。
理由はステップ1の収集が、クラウド環境のネットワーク egress ポリシーで
全滅するため。環境 `env_01XFS6mDoxh5dpWpLnUPVqK2` での実測値：

| 対象 | コンテナ経由(curl) | WebFetch |
|---|---|---|
| 求人ボックス `xn--pckua2a7gp15o89zb.com` | 403 CONNECT 拒否 | EGRESS_BLOCKED |
| 求人ボックス `kyujinbox.com` | 403 CONNECT 拒否 | — |
| スタンバイ `www.stanby.com` / `jp.stanby.com` | 403 CONNECT 拒否 | EGRESS_BLOCKED |
| Indeed `jp.indeed.com` | — | EGRESS_BLOCKED |
| Googleしごと検索 `www.google.com` | 接続不可 | — |
| Wantedly / en-gage | 接続不可 | — |

ポリシーは実質 allowlist（github 等の開発系のみ通る）。
CAPTCHA やサイト側の bot 検知ではなく**環境側の遮断**なので、
ステップ1の「媒体フォールバック方式」では回復しない（3媒体すべて同じ理由で落ちる）。
ステップ1が取れないとステップ2〜4も成立しない。

なお `WebSearch` ツールだけは別経路で通る（コンテナのプロキシを経由しない）。
ただし本日新着（24時間以内）の絞り込み・5ページのページング・
「社名非公開求人を除く」フィルタが効かず、インデックス要約が返るだけなので、
本ルーティンが狙う「毎営業日の新着スイープ」の代替にはならない。
使うなら別設計（recall が大きく落ちることを前提にした縮小版）として作り直す必要がある。

したがって登録先は **会社Mac のローカル cron + ローカル Claude Code**。
クラウド Routine として登録してはいけない（毎営業日9時に
「全媒体ブロック、手動確認要」の DM を撃ち続けるだけになる）。
